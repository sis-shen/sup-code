 ## 2. 产品概述
 
 SupCode 是一个终端原生的智能编程助手，定位为类 Claude Code 的命令行 Coding Agent。它不提供自有的 LLM 能力，而是通过标准化 API 接入各类大语言模型，在终端环境中为开发者提供代码编辑、工程管理和任务执行能力。
 
 **核心定位**：终端原生 + 模型无关 + 可扩展生态

 ## 3. 总体架构
 
 ### 3.1 架构分层（五层模型）
 
 ```
 第1层 交互层 ─── TUI（Bubble Tea）、Slash Command、Skill 加载、多轮对话管理
         │         "用户怎么和 Agent 打交道"
         v
 第2层 引擎层 ─── Agent Loop（ReAct）、LLM Client、SubAgent、Plan Mode
         │         "Agent 怎么自主思考、自主决策"
         v
 第3层 工具层 ─── 内置工具（6 大工具）、MCP 外部工具、Hook 钩子
         │         "Agent 怎么真正动手干活"
         v
 第4层 记忆层 ─── 上下文压缩、Token 管理、长期记忆（SQLite + 向量检索）
         │         "Agent 怎么记得住、又不烧钱"
         v
 第5层 安全层 ─── 五层权限防御、Worktree 隔离、命令过滤、审计日志
                   "Agent 有能力但不失控"
 ```

 **通用设计要求**：
 - 每个工具返回结构化 JSON 数据，方便 Agent 解析决策
 - 工具调用可被 Hook 拦截
 - 支持批量调用和并发执行
 - 所有工具纳入 Permission Engine 管控
 
 ### 4.3 自主任务循环（Agent Loop）
 
 **需求 ID**：F-LOOP-001 ~ F-LOOP-006
 
 基于 ReAct（Reasoning + Acting）范式的核心决策引擎。
 
 | ID | 需求描述 | 优先级 |
 |----|---------|--------|
 | F-LOOP-001 | **任务拆解（Planning）**：Agent 自动将复杂需求拆分为子任务清单，并以有序计划呈现 | P0 |
 | F-LOOP-002 | **工具选择（Tool Selection）**：根据当前上下文和任务进度，动态选择最合适的工具 | P0 |
 | F-LOOP-003 | **结果观察（Observation）**：解析工具返回结果，判断子任务是否完成、是否需要修正 | P0 |
 | F-LOOP-004 | **自我修正（Self-Correction）**：工具执行失败时自动重试或调整策略（最多 3 次重试） | P0 |
 | F-LOOP-005 | **终止条件**：任务完成 / 遇到不可恢复错误 / 达到最大迭代次数（默认 50 次，可配置）时停止 | P0 |
 | F-LOOP-006 | **状态机驱动**：Agent Loop 以明确的状态机实现，状态包含 `Idle -> Planning -> Acting -> Observing -> Completed/Error` | P0 |
 
 **Go 实现约束**：
 - 使用 `context.Context` 贯穿整个 Loop，支持取消和超时
 - 每轮迭代前检查 context 是否已取消
 - 状态变更通过 channel 通知 TUI 层更新

 ## 6. 接口与数据模型
 
 ### 6.1 核心接口定义
 
 ```go
 // LLM 客户端统一接口
 type LLMClient interface {
     Chat(ctx context.Context, req ChatRequest) (<-chan StreamEvent, error)
     Models(ctx context.Context) ([]ModelInfo, error)
 }
 
 // 工具统一接口
 type Tool interface {
     Name() string
     Description() string
     Schema() ToolSchema           // JSON Schema 参数定义
     Execute(ctx context.Context, params json.RawMessage) (ToolResult, error)
 }
 
 // Hook 接口
 type Hook interface {
     Name() string
     Run(ctx context.Context, payload HookPayload) error
 }
 
 // Skill 接口
 type SkillLoader interface {
     Discover() ([]SkillInfo, error)
     Load(ctx context.Context, name string) (Skill, error)
 }
 ```

 | 组件 | 选型 | 理由 |

 | CLI 框架 | `spf13/cobra` | Go 生态事实标准，命令树、自动补全、帮助文档 |

 ## 10. 开发约束与约定
 
 ### 10.1 Go 编码规范
 
 - 遵循 [Effective Go](https://go.dev/doc/effective_go) 和 Go 官方代码风格
 - 使用 `gofmt` / `goimports` 自动格式化
 - 错误处理：使用 `fmt.Errorf` 包装错误（`%w`），不吞没错误
 - 日志：使用 `log/slog`，区分 Info / Debug / Warn / Error 级别
 - 并发：优先使用 `context.Context` 传递取消信号，goroutine 有明确的生命周期管理
 
 ### 10.2 测试要求
 
 - 核心模块（Agent Loop、Tool Registry、Permission Engine）单元测试覆盖率 > 70%
 - 每个工具至少覆盖正常路径 + 错误路径 + 边界条件
 - 集成测试使用真实 LLM API 调用的 mock server 替代
 
 ### 10.3 文档要求
 
 - 每个包提供 `doc.go` 或包级别注释
 - 所有公开函数和类型提供 Go doc 注释
 - 项目 README 包含安装、配置、快速开始指南

 ## 11. 风险与应对
 
 | 风险 | 影响 | Go 层面应对策略 |
 |------|------|---------------|
 | LLM API 成本过高 | 用户流失 | 支持本地模型接口（Ollama 兼容）、Token 预算提醒 |
 | LLM 幻觉导致代码错误 | 信任危机 | 代码审查 Hook、diff 预览确认、测试运行验证 |
 | 终端体验门槛高 | 非目标用户流失 | 清晰的 onboarding 流程（`supcode init` 向导）、`--help` 友好 |
 | Go 并发模型复杂导致 bug | 稳定性下降 | 严格使用 context 取消、goroutine leak 检测（`goleak`）、`-race` 测试 |
 | MCP 协议更新 | 兼容性问题 | MCP 模块独立升级，版本策略与 MCP Spec 对齐 |
 | 危险命令绕过安全机制 | 严重安全事故 | 最小权限原则、审计日志持久化、漏洞奖励计划 |
 > 架构详细设计见 [系统架构设计说明书](系统架构设计说明书.md)。
