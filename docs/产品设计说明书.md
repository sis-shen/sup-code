## 2. 产品概述

### 2.1 产品定位

SupCode 是一款**终端原生（Terminal-Native）的智能编程助手**，定位于类 Claude Code 的命令行交互式 Coding Agent。它不提供自有的 LLM 能力，而是通过标准化的 API 接入各类大语言模型，在终端环境中为开发者提供智能化的代码编辑、工程管理和任务执行能力。

### 2.2 产品愿景

> **将开发者从编码的重复劳动中解放出来，让其回归工程设计与核心决策。**

SupCode 不是替代开发者写代码，而是成为开发者的"外接大脑"与"自动执行臂"——理解自然语言指令，自主规划任务，调用工具链完成高频操作，并在多轮对话中持续积累对项目和用户的理解。

### 2.3 一句话描述

**"一个装在终端里的 AI 编程搭档，能听懂人话、自己动脑子、动手改代码、还懂你的项目。"**

## 3. 目标用户与用户画像

### 3.1 目标受众

- **个人开发者**：独立开发者、自由职业者、开源贡献者
- **技术团队**：中小创业团队的工程师、技术负责人
- **大型组织**：需要标准化开发工作流的企业技术团队

### 3.2 用户画像

#### 画像 A：全栈开发者 Alex
- 每天 80% 时间在写 CRUD、调 API、写测试
- 想快速搭建原型，但不想在重复代码上浪费时间
- 习惯命令行，对 GUI 工具不耐烦
- 使用 SupCode 自然语言描述需求，由 Agent 生成骨架代码、补全测试、自动格式化

#### 画像 B：Tech Lead Bella
- 管理 5-10 人团队，代码审查占用大量时间
- 需要快速理解新接手的遗留项目
- 使用 SupCode 的 Grep/Glob 工具 + 记忆系统，快速梳理项目结构；通过 Agent Teams 分配并行重构任务

#### 画像 C：开源贡献者 Chen
- 经常要给不同项目提 PR、修 Bug
- 每个项目代码风格不同，上手成本高
- 使用 SupCode 的跨会话记忆 + Skill 包，加载项目特定的贡献规范，快速进入状态

## 5. 核心功能模块

### 5.1 终端交互体验（Terminal UI）

**设计原则**：流式响应、边想边输出、多轮对话自然衔接

- **流式渲染**：基于 LLM 的 SSE/Stream 响应实时渲染，用户无需等待完整响应即可看到思考过程
- **Thinking 状态可视化**：Agent 调用工具前显示 "Thinking..."，调用中显示工具名和参数，调用后显示结果摘要
- **多轮对话上下文**：支持连续追问、修正、撤销，对话历史自动维护
- **Markdown 渲染**：代码块、表格、列表在终端内友好渲染
- **编辑会话管理**：支持 `/new` 开启新会话、`/resume` 恢复历史会话

### 5.2 六大核心编程工具

覆盖开发者最高频的六种操作场景：

| 工具名称 | 功能描述 | 典型场景 |
|----------|----------|----------|
| **ReadFile** | 读取指定文件内容，支持指定行范围 | 看源码、读配置、查日志 |
| **WriteFile** | 写入或覆盖文件内容 | 生成新文件、写脚手架 |
| **EditFile** | 基于 diff 的精准编辑，支持查找替换和块级修改 | 改函数、换变量名、调配置 |
| **Bash** | 执行 shell 命令，返回 stdout/stderr/exit code | 跑测试、装依赖、Git 操作 |
| **Glob** | 按模式匹配文件路径 | 找所有 `.test.ts`、遍历 `src/` |
| **Grep** | 按关键字搜索文件内容，支持正则 | 搜函数定义、找 TODO、追踪调用链 |

**设计要点**：
- 每个工具返回结构化数据（JSON/XML），便于 Agent 解析决策
- 工具调用可被 Hook 拦截，实现日志、审计、权限检查
- 支持批量调用和并发执行

### 5.3 自主任务循环（Agent Loop）

基于 **ReAct（Reasoning + Acting）** 范式实现的核心决策引擎：

```
用户输入 -> 理解意图 -> 拆解任务 -> 选择工具 -> 执行工具 -> 观察结果 -> 评估进展 -> [循环] -> 交付结果
```

- **任务拆解（Planning）**：Agent 自动将复杂需求拆分为子任务清单
- **工具选择（Tool Selection）**：根据当前上下文动态选择最合适的工具
- **结果观察（Observation）**：解析工具返回，判断任务是否完成、是否需要修正
- **自我修正（Self-Correction）**：执行失败时自动重试或调整策略
- **终止条件（Termination）**：任务完成、遇到不可恢复错误、或达到最大迭代次数时停止

### 5.4 MCP 协议接入

MCP（Model Context Protocol）是连接外部工具服务的标准化协议：

- **无缝挂载**：任意符合 MCP 规范的服务（GitHub、Slack、数据库、12306 等）通过配置文件即可接入
- **动态发现**：运行时自动发现可用 MCP 服务及其工具列表
- **统一调用**：外部 MCP 工具与内置工具在 Agent Loop 中享受同等待遇
- **安全隔离**：MCP 服务运行在独立进程中，通过 stdio/SSE 通信，崩溃不影响主进程

### 5.5 Skill 技能包系统

将 **Prompt 模板 + 工具组合 + 资源文件** 打包成可装载的独立单元：

- **技能包结构**：
  ```
  my-skill/
  ├── skill.json          # 元数据：名称、版本、描述、依赖
  ├── prompts/
  │   └── system.md       # 系统提示词模板
  ├── tools/
  │   └── custom_tool.py  # 自定义工具实现
  └── resources/
      └── schema.sql      # 配套资源文件
  ```
- **装载方式**：本地路径、Git 仓库、npm 包等多渠道装载
- **热更新**：Skill 更新后无需重启 Agent 即可生效
- **Skill 市场**：内置官方 Skill + 社区共享 Skill 生态

### 5.6 Slash Command 命令框架

内置 + 用户自定义的斜杠命令系统，常用操作一键触发：

- **内置命令示例**：
  - `/new` - 开启新会话
  - `/clear` - 清空当前对话上下文
  - `/skills` - 列出已装载的技能包
  - `/mcp` - 管理 MCP 服务连接
  - `/config` - 查看和修改配置
  - `/exit` - 退出程序
- **自定义命令**：用户通过 YAML/JSON 配置定义自己的快捷命令，绑定到特定的 Prompt 模板或工具链
- **命令发现**：输入 `/` 后自动补全，显示命令描述

### 5.7 Hook 生命周期钩子

在关键节点挂载自定义逻辑，实现深度自动化：

| 钩子点 | 触发时机 | 典型用途 |
|--------|----------|----------|
| `pre_tool_call` | 工具调用前 | 权限校验、参数审查、日志记录 |
| `post_tool_call` | 工具调用后 | 结果审计、自动提交 Git、通知 |
| `pre_session` | 会话开始前 | 加载项目记忆、初始化环境 |
| `post_session` | 会话结束后 | 保存对话摘要、清理临时文件 |
| `pre_agent_loop` | Agent 循环启动前 | 加载 Skill、设置上下文 |
| `post_agent_loop` | Agent 循环结束后 | 生成任务报告、收集反馈 |

### 5.8 五层纵深权限防御

Agent 有能力，但必须可控。五层防御体系：

1. **命令白名单/黑名单**：危险命令（`rm -rf`、`dd`、`mkfs` 等）默认拦截
2. **敏感目录保护**：`~/.ssh/`、`/etc/`、系统目录等需二次确认
3. **写操作确认**：文件覆盖、批量删除等破坏性操作弹出确认提示
4. **未知操作拦截**：首次调用的工具或 MCP 服务需用户授权
5. **审计日志**：所有工具调用记录持久化，支持回溯和复盘

**权限粒度**：可按目录、按工具、按命令设置不同的确认级别（允许/询问/拒绝）。

### 5.9 上下文压缩与 Token 管理

解决长对话场景下的上下文窗口瓶颈：

- **智能压缩**：对话超过阈值后，自动将早期对话摘要压缩为 "记忆卡片"
- **分层上下文**：
  - 当前任务上下文（完整保留）
  - 历史任务摘要（压缩保留）
  - 项目级记忆（长期保留）
- **Token 预算**：为每个会话设置 Token 上限，接近上限时主动提示和压缩
- **关键信息保护**：压缩算法识别并保留关键决策点、错误信息、用户偏好

### 5.10 跨会话记忆系统

Agent 在多次会话之间持续累积理解：

- **项目级记忆（Project Memory）**：
  - 项目结构、模块依赖、命名规范
  - 技术栈、构建流程、测试策略
  - 历史任务和决策记录
- **用户级记忆（User Memory）**：
  - 编码风格偏好（缩进、引号、注释风格）
  - 常用工具链和工作流
  - 个人项目清单和优先级
- **记忆更新**：每次会话结束后自动提取关键信息更新记忆库
- **记忆检索**：新会话启动时自动加载相关记忆，注入系统提示词

### 5.11 SubAgent 子任务分发

将复杂任务委派给独立子 Agent 并行执行：

- **任务拆分**：父 Agent 将大任务拆分为独立的子任务
- **并行执行**：多个 SubAgent 同时运行，各自拥有独立的上下文和工具链
- **结果聚合**：父 Agent 收集各 SubAgent 结果，整合为最终输出
- **资源隔离**：每个 SubAgent 运行在独立的 LLM 连接和上下文环境中
- **典型场景**：同时给多个文件加类型注解、并行跑多组测试、多模块同时重构

### 5.12 Git Worktree 并行隔离

多 Agent 同时改代码时的冲突解决方案：

- **自动 Worktree**：检测到并发写操作时，自动创建 Git Worktree 分支
- **独立工作区**：每个 Agent 在自己的 Worktree 中工作，互不干扰
- **自动合并**：任务完成后，Agent 尝试自动合并变更，冲突时提交人工处理
- **清理机制**：Worktree 合并或废弃后自动清理，保持仓库整洁

### 5.13 Agent Teams 多 Agent 团队

组建长期协作的 Agent 团队，处理跨领域大型项目：

- **角色定义**：为不同 Agent 分配角色（架构师、前端专家、测试工程师、DevOps）
- **协作协议**：Agent 之间通过标准化消息协议通信和交接任务
- **共享上下文**：团队成员共享项目记忆和关键决策，保持认知一致
- **负载均衡**：根据任务类型自动分发给最合适的 Agent
- **人机协作**：关键决策点保留人类审批，Agent 负责执行和实现

## 6. 能力边界

### 6.1 明确不提供的能力

| 边界项 | 说明 |
|--------|------|
| **自研 LLM** | 不内置或训练自有大语言模型，仅支持通过 API 接入第三方 LLM（OpenAI、Claude、DeepSeek、本地模型等） |
| **可视化 GUI** | 不提供图形化界面，纯命令行交互；用户可通过 MCP 接入外部 GUI 工具 |
| **无限上下文** | 受限于所接入 LLM 的上下文窗口大小，超长对话需依赖压缩机制 |
| **网络自由访问** | 不内置浏览器自动化或任意网页爬取能力（可通过 MCP 扩展） |
| **代码执行环境** | 不内置沙箱执行环境，代码运行依赖宿主机的 Bash 工具 |

### 6.2 能力约束

- **LLM 依赖**：Agent 的智能上限取决于所接入 LLM 的能力
- **幻觉风险**：LLM 可能生成错误信息，重要操作需人工确认
- **执行安全**：Agent 通过 Bash 工具执行的命令直接作用于宿主机，权限防御是最后一道防线
- **网络延迟**：流式响应体验受 API 网络延迟影响

## 7. 产品形态与交付物

### 7.1 交付形态

**命令行工具安装包**，支持以下分发渠道：

- **包管理器安装**：`npm install -g supcode`、`pip install supcode`、`cargo install supcode` 等
- **二进制下载**：GitHub Releases 提供各平台预编译二进制文件
- **容器镜像**：Docker 镜像支持 `docker run supcode`
- **一键安装脚本**：`curl -fsSL https://supcode.dev/install.sh | sh`

### 7.2 安装后体验

```bash
# 安装
$ npm install -g supcode

# 首次运行，配置 API Key
$ supcode config set api_key=sk-xxx

# 进入交互会话
$ supcode
> 你好，我是 SupCode。当前项目：my-project。有什么可以帮你？

# 直接执行单次任务
$ supcode "把 utils.ts 里的所有 any 改成具体类型"
```

### 7.3 配置文件

```yaml
# ~/.supcode/config.yaml
llm:
  provider: openai
  model: gpt-4o
  api_key: ${OPENAI_API_KEY}
  max_tokens: 4096

agent:
  max_iterations: 50
  permission_level: ask  # allow / ask / deny

memory:
  project_memory_dir: .supcode/memory
  user_memory_dir: ~/.supcode/memory

mcp:
  servers:
    - name: github
      command: npx -y @modelcontextprotocol/server-github
      env:
        GITHUB_PERSONAL_ACCESS_TOKEN: ${GITHUB_TOKEN}

skills:
  auto_load:
    - @supcode/skills-nodejs
    - ./custom-skills/my-team-rules
```

## 8. 技术架构概述

### 8.1 高层架构图（五层模型）

SupCode 采用**自上而下的五层分层架构**，详细设计见 [系统架构设计说明书](系统架构设计说明书.md)。

```
+------------------------------------------------------------------+
|  第1层  交互层  |  TUI / Slash Command / Skill 加载 / 多轮对话  |
|                 |  "用户怎么和 Agent 打交道"                     |
+------------------------------------------------------------------+
        |
        v
+------------------------------------------------------------------+
|  第2层  引擎层  |  Agent Loop / LLM Client / SubAgent / Plan    |
|                 |  "Agent 怎么自主思考、自主决策"               |
+------------------------------------------------------------------+
        |
        v
+------------------------------------------------------------------+
|  第3层  工具层  |  内置工具 / MCP 外部工具 / Hook 钩子          |
|                 |  "Agent 怎么真正动手干活"                     |
+------------------------------------------------------------------+
        |
        v
+------------------------------------------------------------------+
|  第4层  记忆层  |  上下文压缩 / Token 管理 / 长期记忆           |
|                 |  "Agent 怎么记得住、又不烧钱"                 |
+------------------------------------------------------------------+
        |
        v
+------------------------------------------------------------------+
|  第5层  安全层  |  权限防御 / Worktree 隔离 / 命令过滤 / 审计  |
|                 |  "Agent 有能力但不失控"                       |
+------------------------------------------------------------------+
```

### 8.2 核心模块说明

| 模块 | 职责 | 技术选型建议 |
|------|------|-------------|
| **Terminal UI** | 流式渲染、Markdown 显示、用户输入处理 | TypeScript + Ink / Rich (Python) / Bubble Tea (Go) |
| **Agent Loop** | ReAct 决策循环、任务拆解、自我修正 | 状态机实现，支持可插拔策略 |
| **Tool Registry** | 工具注册、发现、调用、结果格式化 | 统一接口 + 反射/动态加载 |
| **LLM Client** | 多提供商适配、流式处理、重试降级 | 适配器模式，支持 OpenAI SDK / Anthropic SDK |
| **Context Manager** | 对话历史维护、Token 计数、智能压缩 | 滑动窗口 + 摘要算法（如 Map-Reduce） |
| **Memory Store** | 项目记忆和用户记忆的持久化与检索 | SQLite + 向量检索（如 sqlite-vec） |
| **MCP Client** | MCP 协议实现、服务发现、生命周期管理 | 遵循 MCP Spec v1.0 |
| **Hook System** | 生命周期事件分发、插件逻辑挂载 | 事件总线 + 中间件链 |
| **Permission Engine** | 命令过滤、目录保护、操作确认 | 规则引擎 + 白名单/黑名单 |
| **SubAgent** | 子任务分发、并行调度、结果聚合 | Worker Pool + 消息队列 |
| **Git Worktree** | 工作树管理、自动创建、合并清理 | Git CLI 封装 |

## 9. 竞品分析

### 9.1 直接竞品

| 竞品 | 优势 | 劣势 | SupCode 差异化 |
|------|------|------|----------------|
| **Claude Code** | 体验流畅、与 Claude 模型深度优化 | 仅支持 Claude 模型、闭源、需 Anthropic 账号 | 模型无关、开源、MCP 生态 |
| **GitHub Copilot CLI** | 与 GitHub 生态深度集成 | 功能较单一，主要是命令补全和解释 | 完整的 Agent 能力、任务循环 |
| **Aider** | 开源、支持多模型、Git 集成好 | 交互体验较朴素、无 Skill/MCP 扩展 | 更现代的交互 + 可扩展生态 |
| **Cursor** | GUI 强大、IDE 集成深 | 是 GUI 编辑器而非终端工具 | 终端原生、更轻量、更灵活 |

### 9.2 差异化总结

SupCode 的核心差异化在于 **"终端原生 + 模型无关 + 可扩展生态"**：

1. **终端原生**：专为命令行场景设计，不依赖 IDE，SSH 到服务器也能用
2. **模型无关**：不绑定任何单一 LLM，用户可自由选择或切换模型
3. **MCP 生态**：通过标准化协议接入无限外部工具，不被内置能力限制
4. **Skill 系统**：Prompt + 工具 + 资源打包复用，能力像 App Store 一样扩展
5. **Agent Teams**：从单 Agent 助手升级为多 Agent 协作团队，处理更复杂场景

## 10. 里程碑规划

### Phase 1：MVP（最小可用产品）
**目标**：能对话、能读文件、能改代码

## 12. 风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|----------|
| LLM API 成本过高 | 用户流失 | 支持本地模型（Ollama、LM Studio）、Token 预算提醒 |
| LLM 幻觉导致代码错误 | 信任危机 | 强制代码审查 Hook、测试运行验证、 diff 预览确认 |
| 终端体验门槛高 | 非目标用户流失 | 清晰的 onboarding、丰富的文档和示例、友好错误提示 |
| 竞品快速迭代 | 差异化被抹平 | 聚焦开源社区 + MCP 生态、快速响应社区需求 |
| 权限绕过安全漏洞 | 严重安全事故 | 安全审计、最小权限原则、漏洞赏金计划 |

## 13. 附录

### 13.1 术语表

| 术语 | 说明 |
|------|------|
| **Agent** | 智能体，能自主感知环境、做出决策并执行动作的 AI 程序 |
| **ReAct** | Reasoning + Acting，一种让 LLM 交替进行推理和行动的 prompting 范式 |
| **MCP** | Model Context Protocol，OpenAI 提出的标准化工具调用协议 |
| **Skill** | 技能包，封装了特定领域 Prompt、工具和资源的能力单元 |
| **Hook** | 钩子，在特定生命周期节点挂载自定义逻辑的机制 |
| **Token** | LLM 处理文本的最小单位，上下文窗口和计费的基本单元 |
| **Worktree** | Git 功能，允许在同一仓库中检出多个分支到不同目录 |
| **SubAgent** | 子智能体，由父 Agent 派生的独立任务执行单元 |
