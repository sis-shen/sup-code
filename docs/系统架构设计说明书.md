 ## 2. 架构总览：五层模型
 
 SupCode 采用**自上而下的五层分层架构**，每层职责单一、边界清晰，上层依赖下层，下层对上层透明。
 
 ```
 +------------------------------------------------------------------+
 |  第1层  交互层  |  TUI / Slash Command / Skill 加载 / 多轮对话  |
 |                 |  "用户怎么和 Agent 打交道"                     |
 +------------------------------------------------------------------+
         |  user input, stream output, command dispatch
         v
 +------------------------------------------------------------------+
 |  第2层  引擎层  |  Agent Loop / LLM Client / SubAgent / Plan    |
 |                 |  "Agent 怎么自主思考、自主决策"               |
 +------------------------------------------------------------------+
         |  tool calls, MCP requests, hook triggers
         v
 +------------------------------------------------------------------+
 |  第3层  工具层  |  内置工具 / MCP 外部工具 / Hook 钩子          |
 |                 |  "Agent 怎么真正动手干活"                     |
 +------------------------------------------------------------------+
         |  file read/write, context query, memory store
         v
 +------------------------------------------------------------------+
 |  第4层  记忆层  |  上下文压缩 / Token 管理 / 长期记忆           |
 |                 |  "Agent 怎么记得住、又不烧钱"                 |
 +------------------------------------------------------------------+
         |  permission check, worktree isolation, command filter
         v
 +------------------------------------------------------------------+
 |  第5层  安全层  |  权限防御 / Worktree 隔离 / 命令过滤 / 审计  |
 |                 |  "Agent 有能力但不失控"                       |
 +------------------------------------------------------------------+
 ```
 
 **分层原则**：
 - 上层只依赖直接下层，不跨层调用
 - 每层通过 Go interface 暴露能力，内部实现可替换
 - 层间通信通过明确的 Go channel 或 context 传递，不存在隐式依赖

 ## 3. 各层详细设计
 
 ### 3.1 第1层——交互层（Interaction Layer）
 
 **职责**：最贴近用户的一层，决定用 SupCode 的"手感"。
 
 ```
 +------------------+  +------------------+  +------------------+
 |   TUI 界面       |  |   Slash Command  |  |   Skill 加载器   |
 | (Bubble Tea)     |  |   命令解析引擎    |  | (动态发现+注入)  |
 +--------+---------+  +--------+---------+  +--------+---------+
          |                     |                     |
          +---------------------+---------------------+
                                |
                     +----------+----------+
                     |   多轮对话管理器    |
                     | (Session Manager)  |
                     +----------+----------+
                                |
                          (向下交给引擎层)
 ```
 
 | 子模块 | 职责 | Go 实现要点 |
 |--------|------|------------|
 | **TUI 界面** | 流式渲染 LLM 响应、Markdown 展示、Thinking 状态可视化、用户输入处理 | Bubble Tea `Model` 状态机，`tea.Batch` 异步，`glamour` 渲染 |
 | **Slash Command** | 解析 `/` 前缀命令，内置命令 + 用户自定义命令，自动补全 | `trie` 前缀树匹配，命令注册表 `map[string]Command` |
 | **Skill 加载器** | 运行时发现并加载技能包，注入系统提示词，注册 Skill 专属工具 | 文件系统 watch + 热重载，`plugin` 模式（Go 1.18+） |
 | **多轮对话管理器** | 会话创建/切换/恢复，对话历史维护，上下文生命周期 | `Session` struct，SQLite 持久化，内存缓存热会话 |
 
 **对外接口**（供引擎层调用）：
 
 ```go
 // 交互层向上暴露给引擎层的接口
 type InteractionService interface {
     // 发送流式响应给用户
     StreamResponse(ctx context.Context, sessionID string, stream <-chan LLMEvent) error
     // 请求用户确认（权限弹窗等）
     RequestConfirmation(ctx context.Context, sessionID string, prompt ConfirmPrompt) (bool, error)
     // 获取用户输入
     ReadInput(ctx context.Context, sessionID string) (string, error)
     // 处理斜杠命令
     HandleCommand(ctx context.Context, sessionID string, cmd string) (CommandResult, error)
 }
 ```
 
 ### 3.2 第2层——引擎层（Engine Layer）
 
 **职责**：整个系统的"发动机"，Agent 的"大脑 + 心跳"。
 
 ```
 +------------------------------------------------------------------+
 |                       Agent Loop（ReAct 决策引擎）                |
 |  +------------------+  +------------------+  +------------------+ |
 |  |   Task Planner   |  |  Tool Selector   |  | Self-Corrector   | |
 |  |   (任务拆解)      |  |  (工具选择)       |  | (自我修正)        | |
 |  +------------------+  +------------------+  +------------------+ |
 +------------------------------------------------------------------+
          |                       |                       |
          v                       v                       v
 +------------------+  +------------------+  +------------------+
 |   LLM Client     |  | SubAgent         |  |   Plan Mode      |
 | (多供应商适配)    |  | Orchestrator     |  | (Plan/Act 分离)  |
 +------------------+  +------------------+  +------------------+
 ```
 
 | 子模块 | 职责 | Go 实现要点 |
 |--------|------|------------|
 | **Agent Loop** | ReAct 范式核心循环：理解意图 -> 拆解任务 -> 选择工具 -> 执行 -> 观察 -> 修正 -> 交付 | 状态机（`Idle/Planning/Acting/Observing/Completed/Error`），`context.Context` 贯穿 |
 | **Task Planner** | 将复杂自然语言需求拆分为有序子任务清单 | 调用 LLM 生成结构化 Plan，解析为 `[]PlanItem` |
 | **Tool Selector** | 根据当前上下文和任务进度，从工具层选取最合适的工具 | 基于工具描述 + LLM function calling 的语义匹配 |
 | **Self-Corrector** | 工具执行失败时自动重试或调整策略 | 指数退避重试（最多 3 次），错误分类（可恢复/不可恢复） |
 | **LLM Client** | 多供应商抽象层，流式 SSE 处理，重试降级 | `LLMClient` interface，各供应商独立子包，纯 `net/http` |
 | **SubAgent Orchestrator** | 将大任务委派给独立子 Agent 并行执行，收集聚合结果 | goroutine pool + channel，每个 SubAgent 独立 context |
 | **Plan Mode** | Plan/Act 分离模式：先出计划等待确认，确认后再执行 | 引擎层状态机扩展，`Planning` -> `WaitingApproval` -> `Acting` |
 
 **核心循环伪代码**：
 
 ```go
 func (a *Agent) Run(ctx context.Context, input string) (*Result, error) {
     a.setState(Planning)
     plan, err := a.planner.Plan(ctx, input)
     if err != nil { return nil, err }
 
     for _, step := range plan.Steps {
         select {
         case <-ctx.Done():
             return nil, ctx.Err()
         default:
         }
 
         a.setState(Acting)
         tool, err := a.selector.Select(ctx, step)
         if err != nil { return nil, err }
 
         result, err := a.executeTool(ctx, tool, step.Params)
         if err != nil {
             // Self-correction
             result, err = a.corrector.Retry(ctx, tool, step.Params, err)
             if err != nil { return nil, err }
         }
 
         a.setState(Observing)
         if a.isComplete(plan, result) {
             break
         }
     }
 
     a.setState(Completed)
     return a.finalize(plan)
 }
 ```
 
 ### 3.3 第3层——工具层（Tool Layer）
 
 **职责**：Agent 的"手"，让它能真的读文件、写代码、跑命令。
 
 ```
 +------------------------------------------------------------------+
 |                       Tool Registry（工具注册中心）               |
 |  统一注册、发现、调用、结果格式化                                  |
 +------------------------------------------------------------------+
          |                       |                       |
          v                       v                       v
 +------------------+  +------------------+  +------------------+
 |   内置工具集      |  |   MCP Client     |  |   Hook Engine    |
 | ReadFile         |  | (stdio/SSE 协议) |  | pre/post 钩子链  |
 | WriteFile        |  +------------------+  +------------------+
 | EditFile         |           |
 | Bash             |           v
 | Glob             |  +------------------+
 | Grep             |  |   MCP Servers    |
 +------------------+  | (外部独立进程)   |
                       +------------------+
 ```
 
 | 子模块 | 职责 | Go 实现要点 |
 |--------|------|------------|
 | **Tool Registry** | 统一的工具注册、发现、调用、结果格式化中心 | `map[string]Tool`，`Tool` interface，线程安全（`sync.RWMutex`） |
 | **六大内置工具** | ReadFile / WriteFile / EditFile / Bash / Glob / Grep | 各自实现 `Tool` interface，返回结构化 JSON |
 | **MCP Client** | 遵循 MCP Spec 的客户端协议实现，支持 stdio 和 SSE 传输 | 独立 goroutine 管理 MCP 服务进程生命周期，JSON-RPC 通信 |
 | **MCP Servers** | 外部工具服务，运行在独立进程中 | 通过 `os/exec` 启动，stdio/SSE 通信，崩溃隔离 |
 | **Hook Engine** | 在工具调用前后执行钩子链，支持拦截、修改参数、审计 | 中间件链模式，`pre -> tool -> post`，超时控制 30s |
 
 **Tool 接口定义**：
 
 ```go
 // 所有工具实现此接口
 type Tool interface {
     Name() string
     Description() string
     Schema() ToolSchema               // JSON Schema，供 LLM function calling 使用
     Execute(ctx context.Context, params json.RawMessage) (ToolResult, error)
 }
 
 // Tool Registry
 type ToolRegistry struct {
     mu    sync.RWMutex
     tools map[string]Tool
     hooks []Hook                      // 全局钩子链
 }
 
 func (r *ToolRegistry) Execute(ctx context.Context, name string, params json.RawMessage) (ToolResult, error) {
     // 1. 执行 pre_tool_call 钩子
     // 2. 执行工具
     // 3. 执行 post_tool_call 钩子
 }
 ```
 
 ### 3.4 第4层——记忆层（Memory Layer）
 
 **职责**：专治"Agent 怎么记得住、又不烧钱"。上下文压缩 + 长期记忆双管齐下。
 
 ```
 +------------------------------------------------------------------+
 |                     Context Manager（上下文管理器）               |
 |  消息历史维护 / Token 计数 / 压缩决策 / 分层存储                  |
 +------------------------------------------------------------------+
          |                       |                       |
          v                       v                       v
 +------------------+  +------------------+  +------------------+
 |   短期上下文      |  |   上下文压缩器    |  |   长期记忆库      |
 | (内存消息列表)    |  | (Map-Reduce 摘要)|  | (SQLite + Vec)  |
 +------------------+  +------------------+  +------------------+
                                |                       |
                                v                       v
                       +------------------+  +------------------+
                       |   记忆卡片        |  |  向量检索引擎    |
                       | (压缩后的摘要)    |  | (语义相似搜索)   |
                       +------------------+  +------------------+
 ```
 
 | 子模块 | 职责 | Go 实现要点 |
 |--------|------|------------|
 | **Context Manager** | 消息历史维护、Token 实时计数、压缩决策、分层存储调度 | 滑动窗口算法，Token 计数集成 `tiktoken-go`，阈值触发压缩 |
 | **短期上下文** | 当前会话的完整消息历史，内存中维护 | `[]Message` 切片，带 Token 元数据 |
 | **上下文压缩器** | 当消息量超阈值时，调用 LLM 生成早期对话摘要 | Map-Reduce 策略：分段摘要 -> 合并摘要，非阻塞异步执行 |
 | **记忆卡片** | 压缩后的摘要，结构化为关键决策、错误信息、用户偏好 | `MemoryCard` struct，注入后续消息的系统提示词 |
 | **长期记忆库** | 项目级和用户级记忆的持久化存储和检索 | SQLite + `sqlite-vec` 向量扩展，语义相似度检索 |
 | **向量检索引擎** | 基于嵌入向量的语义搜索，新会话启动时检索相关记忆 | 调用 LLM embedding API 生成向量，余弦相似度排序 |
 
 **分层记忆模型**：
 
 | 记忆类型 | 存储位置 | 生命周期 | 容量 | 检索方式 |
 |---------|---------|---------|------|---------|
 | 当前任务上下文 | 内存 `[]Message` | 单次 Agent Loop | 完整保留 | 顺序访问 |
 | 会话记忆卡片 | 内存 + SQLite | 单次会话 | 压缩摘要 | 注入系统提示词 |
 | 项目级记忆 | SQLite + 向量 | 跨会话持久 | 无限 | 语义检索 Top-K |
 | 用户级记忆 | SQLite + 向量 | 永久 | 无限 | 语义检索 Top-K |
 
 ### 3.5 第5层——安全层（Security Layer）
 
 **职责**：最底层的"安全刹车"，让 Agent 有能力但不失控。
 
 ```
 +------------------------------------------------------------------+
 |                    Permission Engine（权限引擎）                  |
 |  统一的权限决策中心                                               |
 +------------------------------------------------------------------+
          |                       |                       |
          v                       v                       v
 +------------------+  +------------------+  +------------------+
 |   命令过滤器      |  |   目录保护器      |  |   操作确认器      |
 | (黑白名单匹配)    |  | (敏感路径拦截)    |  | (级联确认策略)    |
 +------------------+  +------------------+  +------------------+
          |                       |                       |
          +-----------------------+-----------------------+
                                  |
                                  v
 +------------------------------------------------------------------+
 |                        审计日志（Audit Logger）                   |
 |  所有工具调用记录 / 权限决策 / 可回溯复盘                          |
 +------------------------------------------------------------------+
                                  |
                                  v
 +------------------------------------------------------------------+
 |                    Worktree Manager（工作区隔离）                  |
 |  并发写操作自动隔离 / 自动合并 / 清理                              |
 +------------------------------------------------------------------+
 ```
 
 **五层纵深防御**：
 
 | 层级 | 机制 | 策略 | Go 实现 |
 |------|------|------|---------|
 | 1 | 命令黑白名单 | 危险命令（`rm -rf`、`dd`、`mkfs`）默认拦截 | 正则匹配 + 可配置名单 |
 | 2 | 敏感目录保护 | `~/.ssh/`、`/etc/`、系统目录操作需二次确认 | 路径前缀匹配 |
 | 3 | 写操作确认 | 覆盖/批量删除等破坏性操作弹确认 | 按操作类型分级 |
 | 4 | 未知操作拦截 | 首次调用的工具/MCP 服务需授权 | 首次使用标记 |
 | 5 | 审计日志 | 所有调用记录持久化，支持回溯 | SQLite `audit_logs` 表 |
 
 **权限决策模型**：
 
 ```go
 type PermissionEngine struct {
     rules       []PermissionRule
     auditLogger *AuditLogger
 }
 
 type PermissionRule struct {
     Scope    string   // "command" / "path" / "tool" / "mcp"

     Decision Decision // allow / ask / deny
 }
 
 func (p *PermissionEngine) Check(ctx context.Context, action Action) (Decision, error) {
     // 按优先级依次检查规则
     // 记录审计日志
     // 返回 allow / ask（触发交互层确认） / deny
 }
 ```

 ## 4. 层间数据流
 
 ### 4.1 一次完整的用户请求生命周期
 
 ```
 用户输入: "把 utils.ts 里的所有 any 改成具体类型"
 
 [交互层] 接收输入 -> 交给引擎层
     |
 [引擎层] Agent Loop 启动
     |-- Planning: 调用 LLM 拆解任务
     |   计划: 1. Glob 找到 utils.ts
     |         2. Grep 找到所有 any
     |         3. ReadFile 读取上下文
     |         4. EditFile 逐个替换
     |         5. Bash 运行类型检查
     |
     |-- Acting Step 1: 调用工具层 Glob
     |       |
     |       [安全层] 检查 Glob 调用权限 -> allow
     |       [工具层] 执行 Glob("utils.ts") -> ["src/utils.ts"]
     |
     |-- Acting Step 2: 调用工具层 Grep
     |       |
     |       [安全层] 检查 Grep 调用权限 -> allow
     |       [工具层] 执行 Grep("any", "src/utils.ts") -> [line 3, line 7, line 12]
     |
     |-- Acting Step 3: ReadFile + EditFile
     |       |
     |       [安全层] 检查写操作 -> ask（弹出确认）
     |       [交互层] 显示确认提示 -> 用户确认
     |       [工具层] 执行 EditFile 替换
     |
     |-- Acting Step 4: Bash
     |       |
     |       [安全层] 检查 Bash 命令 -> allow
     |       [工具层] 执行 "npx tsc --noEmit" -> 结果
     |
     [引擎层] Observing: 类型检查通过
     [引擎层] Completed -> 通知交互层
     |
 [交互层] 流式渲染结果给用户
 
 [记忆层] 后台异步: 提取关键信息更新记忆库
 ```
 
 ### 4.2 层间调用约束
 
 | 调用方向 | 是否允许 | 通信方式 |
 |---------|---------|---------|
 | 交互层 -> 引擎层 | 允许 | Go interface 方法调用 |
 | 交互层 -> 工具层 | **禁止** | 必须经过引擎层 |
 | 交互层 -> 记忆层 | **禁止** | 必须经过引擎层 |
 | 引擎层 -> 工具层 | 允许 | Go interface 方法调用 |
 | 引擎层 -> 记忆层 | 允许 | `ContextManager` interface |
 | 安全层 -> 所有层 | **横切关注点** | 以中间件形式嵌入工具层，以确认回调形式嵌入引擎层和交互层 |

 ## 5. 分阶段架构演进
 
 ### 5.1 Phase 1 — MVP 架构骨架
 
 **目标**：能对话、能读文件、能改代码。最小五层骨架，只实现各层的核心子模块。
 
 ```
 [交互层]  TUI（Bubble Tea 基础输入/输出）
           Slash Command（仅 /new /exit）
           |
 [引擎层]  Agent Loop（ReAct 状态机，单轮工具调用）
           LLM Client（仅 OpenAI）
           |
 [工具层]  Tool Registry（简单 map 注册）
           六大内置工具
           |
 [记忆层]  短期上下文（内存消息列表）
           Token 计数（基础 tiktoken）
           |
 [安全层]  命令黑白名单
           敏感目录保护
 ```
 
 | 模块 | MVP 实现范围 | 延后内容 |
 |------|------------|---------|
 | 交互层 | 基础输入/输出、流式渲染、Markdown 显示、`/new` `/exit` | Skill 加载、自动补全、会话列表 |
 | 引擎层 | Agent Loop 状态机、OpenAI 适配器、单轮任务拆解 | SubAgent、Plan Mode 分离、Self-Correction |
 | 工具层 | 六大工具 + 简单 Register | MCP、Hook Engine |
 | 记忆层 | `[]Message` 内存存储、基础 Token 计数 | 上下文压缩、长期记忆、向量检索 |
 | 安全层 | 命令黑白名单（正则）、敏感目录拦截 | 完整五层体系、审计日志 |
 
 ### 5.2 Phase 2 — 增强架构
 
 **目标**：更好用、更安全、更智能。补充记忆层和引擎层的核心能力。
 
 ```
 [交互层]  TUI（自动补全、会话管理 /resume）
           Slash Command（自定义命令支持）
           |
 [引擎层]  Agent Loop（Self-Correction 完善）
           LLM Client（多供应商：OpenAI + Claude + DeepSeek）
           Plan Mode（Plan/Act 分离）
           |
 [工具层]  Tool Registry（完善）
           Hook Engine（pre/post 钩子链）
           六大内置工具
           |
 [记忆层]  上下文压缩器（Map-Reduce）
           长期记忆库（SQLite + 项目/用户记忆）
           记忆卡片机制
           |
 [安全层]  五层纵深防御（完整）
           审计日志（SQLite）
 ```
 
 | 新增/增强 | 说明 |
 |----------|------|
 | 上下文压缩器 | 会话超阈值后异步触发，生成记忆卡片注入后续对话 |
 | 长期记忆库 | SQLite 持久化项目结构和用户偏好，新会话自动注入系统提示词 |
 | Hook Engine | 中间件链模式，pre -> tool -> post，支持修改参数和拦截 |
 | Plan Mode | 引擎层新增 `WaitingApproval` 状态，交互层显示计划并等待确认 |
 | 多供应商 LLM | `LLMClient` interface 增加 Anthropic、DeepSeek、Ollama 实现 |
 
 ### 5.3 Phase 3 — 生态架构
 
 **目标**：可扩展、可复用、可协作。打开工具层和交互层的外部扩展能力。
 
 ```
 [交互层]  TUI（完善）
 ```

 ## 7. 关键设计决策
 
 ### 7.1 为什么安全层在最底层
 
 安全层以**横切关注点**形式嵌入工具层（pre/post hook），以**确认回调**形式渗透到引擎层和交互层。物理上它作为独立包存在，但在调用链上它包裹在工具执行的外层，形成"安全刹车"——所有操作必须先过安全层。
 
 ```
 引擎层调用工具
     -> 安全层.PreCheck()
         -> allow: 继续
         -> ask: 回调交互层弹确认框 -> 等待用户决策
         -> deny: 直接拒绝，返回错误
     -> 工具层.Execute()
     -> 安全层.PostAudit()
 ```
 
 ### 7.2 为什么记忆层独立为一层
 
 记忆不是引擎层的附属功能，而是独立的横向能力。原因：
 - 上下文压缩需要在 LLM 调用之外独立运行（异步非阻塞）
 - 长期记忆的存储和检索有自己的存储方案（SQLite + 向量），与引擎层逻辑解耦
 - 记忆卡片需要独立的生命周期管理（生成、更新、过期）
 - 未来可能需要升级为外部向量数据库，独立成层后替换成本低
 
 ### 7.3 Go 并发模型与分层的关系
 
 - **交互层**：Bubble Tea 单 goroutine ELM 循环，通过 channel 接收引擎层事件
 - **引擎层**：Agent Loop 在独立 goroutine 中运行，通过 context 控制生命周期，通过 channel 推送状态到交互层
 - **工具层**：每个工具调用可独立 goroutine，`ToolRegistry.Execute` 线程安全（`sync.RWMutex`）
 - **记忆层**：压缩任务异步 goroutine，不阻塞 Agent Loop
 - **安全层**：同步调用（权限决策必须即时），审计日志写入可异步批量

 ## 8. 架构约束与原则
 
 1. **单向依赖**：上层依赖下层，下层绝不依赖上层。`internal/tools` 不能 import `internal/agent`。
 2. **接口隔离**：层间通过 Go interface 通信，不依赖具体实现。`internal/agent` 依赖 `Tool` interface，不依赖 `internal/tools/readfile` 具体实现。
 3. **配置注入**：所有外部依赖（LLM 供应商、MCP 服务、Skill 路径）通过配置注入，不硬编码。
 4. **错误边界**：每层处理自己职责范围内的错误，向上层返回明确错误信息，不吞没。
 5. **无 CGO 优先**：核心路径不依赖 CGO，保证交叉编译简洁。SQLite 使用 `modernc.org/sqlite`（纯 Go 实现）。
 6. **安全默认**：权限引擎默认 deny 未知操作，用户需显式配置 allow。
